# 让系统更可解释

## 采用顺序：先事实，后意图，再说明

Atlas 适合渐进式采用。不要试图先给全部类打注解；先让代码中已经明确的事实被提取出来，再只为“代码无法可靠表达的业务语义”补充 Intent。

| 阶段 | 要做什么 | 成功标准 |
| --- | --- | --- |
| 1. 静态事实 | 运行 `extract`，查看 coverage 和诊断 | 能看到真实路由、事件、消费者、投影/表等已有关系 |
| 2. 稳定意图 | 给关键概念、规则、事件、投影、流程、接口添加 `@Atlas…` | 业务页面出现稳定名称、职责、业务意义 |
| 3. 人工说明 | 规划并维护受控业务/运维内容 | 说明能附着到稳定资产，而不是散落在代码注释里 |
| 4. 运行态 | 安全导入离线观测 | 运维页面能给出有采集时间的状态与建议 |

当前模型、Schema 和读取模型已支持 Content Bundle，但 CLI 的 `extract` 目前传入空 Content Bundle；私有内容包自动读取尚未接入这条命令。因此阶段 3 应先作为治理设计和后续扩展工作，而不要宣传为现成的 CLI 功能。

## 该注解什么，不该注解什么

| 注解 | 应表达的业务意图 | 不应重复的技术事实 |
| --- | --- | --- |
| `@AtlasContext` | 限界上下文的稳定 ID、名称、描述 | Maven 模块名、包扫描 |
| `@AtlasAggregate` | 聚合承担的一致性职责 | Axon 聚合配置 |
| `@AtlasConstraint` | 规则的业务意义、类型、执行提示 | 重复写正则/guard 的实现细节 |
| `@AtlasEvent` | 事件代表的业务事实、关键字段语义 | Event Store、序列化器 |
| `@AtlasProjection` | 读模型服务的业务目的 | JPA 表、SQL、缓存 |
| `@AtlasProcessManager` | 跨聚合流程职责和完成条件 | association key、Deadline 代码 |
| `@AtlasEndpoint` | 外部操作的业务名称和目的 | HTTP method、路由、参数类型 |

例如，规则不要只写“`^[A-Z]{2}-\\d{6}$`”。应先给使用者一句话：

```java
@AtlasConstraint(
    id = "order-id-format",
    name = "订单身份格式",
    businessMeaning = "订单编号由两位业务前缀和六位流水号组成。",
    enforcedBy = "OrderId.of")
```

正则、`Pattern.compile`、执行方法和测试会由静态分析保留为证据；业务页面默认展示 `businessMeaning`，专家页面才展开技术细节。

## 写好业务语言的四条规则

1. **使用稳定身份。** ID 不要只依赖类名、路由或表名；重构后历史 Package 和内容仍需要关联。
2. **写职责和结果。** “维护订单创建前的一致性”优于“OrderAggregate”。“使进度可查询”优于“Projection”。
3. **说明影响与行动。** 规则失败时用户要做什么？流程等待时谁负责下一步？
4. **承认不知道。** 无法确认的业务含义显示为待补充，胜过伪造一个看似合理的名称。

## 冲突时谁说了算

注解是 **DECLARED（已声明）**，代码关系是 **DERIVED（已推导）**，运行导出是 **RUNTIME_OBSERVED（运行观察）**。它们可能冲突，Atlas 不应静默选择一个覆盖另一个。

实际处理顺序应是：

1. 在专家视图定位冲突的 Evidence；
2. 确认 Package 对应的 `sourceRevision`；
3. 修正过期代码、过期 Intent 或错误导出；
4. 重新生成 Package，并保留诊断直到冲突消失。

`Convention Profile` 只描述“如何发现事实”，不能直接制造业务节点或声明流程已运行。详细注解字段与处理器配置见[注解、处理器与意图产物](../annotation-guide/01-注解、处理器与意图产物.md)。
