# 按角色阅读 Atlas

同一份 Package 有三种读取模型。请不要为了“信息更多”而让业务人员打开专家页面，也不要为了“页面简单”而把运维状态压缩成一个绿色圆点。

## 业务地图：先回答业务如何运作

业务页面使用 `/business`。推荐按下列顺序阅读：

1. **领域规则**：什么条件不允许违反？它约束哪个概念？失败后应该如何处理？
2. **业务事件**：发生了什么业务事实？事件携带哪些业务身份或关键事实？
3. **消费者与投影结果**：谁会处理它？哪些查询或业务数据会更新？
4. **自动流程**：从什么事件开始、正在等待什么、什么事件完成、后续会发出什么动作？
5. **外部接口**：这个 API 的业务目的和会触发的命令是什么？

业务页面中的“投影目的地”表达的是可见业务数据，不要求读者理解 JPA、Repository 或表名。它可以回答“提交之后进度在哪里看”，但不会承诺“数据已在生产库更新”。后者属于运行态问题。

## 运维页面：先确认观测是否存在

运维页面使用 `/operations`。打开后第一件事不是看状态卡片，而是看 `runtimeAvailability`：

| 页面提示 | 正确含义 | 不能得出的结论 |
| --- | --- | --- |
| `NOT_CAPTURED` | 当前 Package 没有 Runtime Overlay | 不能说成功、失败或 UNKNOWN |
| `AVAILABLE` | 有一次受控的离线采集 | 不能认为结果永远新鲜或覆盖全部处理器 |

有观测时，资产状态才有意义：

- **已处理（`SUCCEEDED`）**：最近一次可关联处理完成；若业务仍不可见，检查查询条件、权限和数据可见范围。
- **处理失败（`FAILED`）**：数据可能没有反映该事件；先看安全错误分类、重试信息和静态写入目标。
- **存在积压（`LAGGING`）**：处理尚未赶上；检查处理组吞吐、事件积压和目标可用性。
- **正在重试（`RETRYING`）**：恢复中；观察重试次数和错误分类，达到阈值后人工介入。
- **无法判断（`UNKNOWN`）**：本批次没有唯一关联记录；先检查采集范围，绝不当作成功。

运行态页面只返回白名单属性，如延迟、重试次数、错误分类和处理组。原始事件 payload、异常正文和堆栈不会因为“运维需要排查”而进入浏览器。

## 专家模式：每条关系都可回到证据

专家页面使用 `/expert` 和 `/assets/{assetId}`。它适合回答：

- 哪个 Endpoint 经过哪些已确认调用边到达命令或领域动作？
- 某事件由谁生产、被谁消费、投影最后写到哪些目标？
- 这条关系来自源码、注解还是运行观测？
- 某个资产的属性、入边、出边和安全运行记录是什么？

调用路径是有限深度、无循环的静态路径。没有画出的调用不是“被隐藏”，而是当前没有可证明的边，或已达到保护可读性的路径上限。

### 查看源码时的四个前提

1. 用户主动点击某个专家资产；
2. 该资产在当前 Package 中存在；
3. 它自身或唯一的 `REPRESENTS → CodeElement` 映射可定位；
4. runner 用 `--enable-expert-source` 启动，且 Workspace 显式声明了 source JAR。

若映射不唯一，服务会拒绝返回源码，而不是“选第一个”。返回内容不会包含归档的本机绝对路径。

## 一个共同原则：不要跨视图重新推理

- 业务页面只读 `/business`，不从专家调用边自行拼一个业务流程；
- 运维页面只读 `/operations`，不把无运行态的静态关系当作处理成功；
- 专家页面可读证据和源码，但不能把技术细节直接当成业务解释；
- 任何页面看到空内容时，都先检查 coverage 和 diagnostics。

HTTP 路由、错误码和字段语义可查阅[角色化查询与 HTTP 服务](../api/01-角色化查询与HTTP服务.md)，浏览器操作细节见[atlas-web：角色化 Explorer](../web/01-atlas-web.md)。
