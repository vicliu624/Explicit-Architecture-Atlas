# 本地开发、构建与发布

## 前置条件

| 工具 | 基线 | 用途 |
| --- | --- | --- |
| JDK | 21 或更高 | 编译所有 Maven 工件；Parent POM 明确要求 21+ |
| Maven | 3.9 或更高 | 构建 Reactor、测试、生成处理器产物 |
| Node.js | 22 或更高 | 仅校验和构建独立 Web 工程 |
| PowerShell 7+ | 推荐 | 运行仓库结构校验脚本 |

Maven 模块使用 Java 21 的语言/字节码基线，以保证发布物可被 Java 21 环境消费。使用更高版本 JDK（例如 JDK 22）进行本地构建是允许的，只要 Maven Enforcer 校验通过。

## 第一次构建

在仓库根目录依次执行：

```powershell
mvn -B verify
npm --prefix ui-layer/atlas-web run check
pwsh ./scripts/verify-structure.ps1
```

三条命令检查的对象不同：

| 命令 | 验证内容 |
| --- | --- |
| `mvn -B verify` | Parent/BOM/Contract、所有可发布 JAR、Plugin、CLI、fixture 与 JUnit 测试 |
| `npm --prefix ... run check` | Web shell 的 JavaScript 语法；不需要安装前端框架依赖 |
| `verify-structure.ps1` | Reactor 是否包含关键模块、目录边界和关键文档是否存在 |

`integration-test/fixture-projects/strict-explicit-java-sample` 会在 Maven 编译过程中调用注解处理器。成功后可以检查其构建输出中的：

```text
target/classes/META-INF/explicit-architecture-atlas/atlas-intent.json
```

这证明最小闭环“通用显式架构样例 → 编译期意图索引”可用，且完全不依赖任何真实业务项目。`atlas extract` 会再把这个索引与 JVM/Maven 事实归一为完整的 Atlas Package。

## 常用开发命令

只构建一个模块及其所需依赖：

```powershell
mvn -B -pl infra-driven/atlas-source-jvm -am test
```

只验证 Maven Plugin：

```powershell
mvn -B -pl infra-driving/atlas-maven-plugin -am verify
```

构建并查看独立 CLI：

```powershell
mvn -B -pl infra-driving/atlas-cli -am package
java -jar infra-driving/atlas-cli/target/explicit-architecture-atlas-cli-0.0.1.jar --help
```

用私有 Workspace 执行第一条真实提取链路：

```powershell
java -jar infra-driving/atlas-cli/target/explicit-architecture-atlas-cli-0.0.1.jar extract `
  --workspace workspace/local/atlas-workspace.yaml `
  --package-id package:my-project:2026-07-31 `
  --source-revision <git-commit-or-working-tree>
```

`extract` 始终读取 Maven Reactor/直接依赖、生产 Java 源码、编译期 Intent Manifest 和可选 Convention Profile。Spring MVC、Axon、JPA 等事实仅在对应 adapter 已通过 starter 或消费者 POM 放入 classpath 时才提取；普通 CLI 不会暗中引入它们。输出写到 Workspace 同级的 `packages/` 目录。每项实际运行的分析能力都会在 Package Manifest 中声明 `COMPLETE`、`PARTIAL`、`NOT_IMPLEMENTED` 等覆盖状态，不能把未安装能力误解为业务关系不存在。

## 在被分析工程中使用 Maven Plugin

`atlas:extract` 是可执行 goal，不需要启动 CLI。它默认绑定到 `package`，在当前 Maven 项目的 `target/atlas/packages/` 下写出 Atlas Package；该默认路径受 `target/` 管理，因此不会把业务源码、凭据或私有 Workspace 写入版本库。

```xml
<plugin>
  <groupId>io.github.vicliu624.explicitarchitecture</groupId>
  <artifactId>explicit-architecture-atlas-maven-plugin</artifactId>
  <version>${atlas.version}</version>
  <executions>
    <execution>
      <goals><goal>extract</goal></goals>
      <configuration>
        <!-- CI 应传入不可变 commit SHA；不要用本机绝对路径作为身份。 -->
        <sourceRevision>${git.commit.id}</sourceRevision>
        <packageId>package:billing:${git.commit.id}</packageId>
        <sourceRoots><sourceRoot>src/main/java</sourceRoot></sourceRoots>
        <excludedPaths><excludedPath>src/legacy/java</excludedPath></excludedPaths>
      </configuration>
    </execution>
  </executions>
</plugin>
```

未配置时，插件使用 Maven `groupId/artifactId/version` 确定 `projectId`、`packageId` 与 `sourceRevision`，扫描默认生产源码根，并自动读取注解处理器写入的 `target/classes/META-INF/explicit-architecture-atlas/atlas-intent.json`。`conventionProfile`、`intentManifests`、`sourceRoots`、`excludedPaths` 和 `outputDirectory` 均可在 plugin configuration 中显式覆盖；所有相对路径都以 `project.basedir` 为基准。

插件只自带 `atlas-source-jvm` 与 `atlas-maven-source`。要解释 Spring Bean、条件与场景调用，必须把 Spring adapter 作为 **plugin dependency** 明确加入；同理，Axon/JPA 也必须显式选择：

```xml
<plugin>
  <groupId>io.github.vicliu624.explicitarchitecture</groupId>
  <artifactId>explicit-architecture-atlas-maven-plugin</artifactId>
  <version>${atlas.version}</version>
  <dependencies>
    <dependency>
      <groupId>io.github.vicliu624.explicitarchitecture</groupId>
      <artifactId>explicit-architecture-atlas-spring-source</artifactId>
      <version>${atlas.version}</version>
    </dependency>
  </dependencies>
</plugin>
```

这些 adapter 通过 `ServiceLoader` 被发现，未选择的框架不会进入普通插件的依赖图。Maven Plugin 只负责静态 Package；命名场景、私有脱敏配置和运行态 overlay 继续应由受控 Workspace 的 CLI/Server 路径提供。

运行结构脚本时请从任意目录调用完整脚本路径；脚本通过自身位置计算仓库根目录，不依赖当前工作目录。

## 新增一个分析适配器

假设要支持一种新的技术事实来源，按以下顺序实施：

1. 先在 `infra-driven/` 下创建 `atlas-<technology>-source` 模块；它只依赖 `atlas-analysis-spi` 和该技术 SDK。
2. 实现 `SourceFactsAnalyzer`，输出带证据、关系、诊断和覆盖状态的 `AnalyzerContribution`；不要让分析器直接返回 Web DTO 或写入浏览器缓存。
3. 在根 `pom.xml` 注册模块，并视其是否为公共稳定能力决定是否在 `atlas-bom` 管理版本。
4. 为该技术创建通用 fixture 或最小测试；不能依赖本机真实项目目录。
5. 在 `atlas-server-bootstrap` 中以可选方式装配它；“未启用”必须在数据中与“没有发现关系”区分。
6. 更新工程结构、依赖规则和产物契约文档。

若某能力是 Atlas 的输入方式（例如 Gradle 插件、IDE 命令），应放到 `infra-driving/`；若只是读取外部事实（例如 Kafka 消费状态），应放到 `infra-driven/`。

## 新增领域模型或契约字段

稳定模型变更需要同时考虑 Maven 兼容性和数据包兼容性：

1. 在 `atlas-domain-model` 中定义 JDK-only 类型，并保持构造器验证明确；
2. 如数据包也需要该概念，在 `atlas-contract` 中演进对应 Schema；
3. 更新 `schemaVersion` 的兼容策略，禁止让旧渲染器静默误读新字段；
4. 增加 fixture 与集成测试，验证事实、意图和内容的关联；
5. 在变更日志/ADR 中说明是否破坏二进制、源码或 Schema 兼容性。

不要为了图省事把 Spring、Axon 或 JSON 库类型放入领域记录。领域模型是发布边界最内层，技术类型会把所有消费者锁死在同一框架版本上。

## 发布流程

`0.0.1` 起，公开 Maven 工件的目标是 GitHub Packages Maven Registry，而不是未配置凭据的 Maven Central。发布地址由 Parent POM 的 `distributionManagement` 统一声明：

```text
https://maven.pkg.github.com/vicliu624/Explicit-Architecture-Atlas
```

不要在开发机直接执行 `deploy`。正式流程必须由 GitHub Actions 完成：

1. 将非 `-SNAPSHOT` 的版本、`CHANGELOG.md` 和发布所需文档合并到 `main`；
2. 等待 `.github/workflows/ci.yml` 的 CI 通过 Maven、Web shell 与目录边界校验；
3. 创建并推送带注释的 `v<version>` tag；
4. `release.yml` 校验 tag 与 Maven 版本一致，在 `release` Profile 下发布 Parent、BOM、Contract、领域/应用模块、SPI、适配器、Plugin、CLI、starter、HTTP 和 Server 工件；根 Reactor、fixture 与集成测试模块继续跳过 deploy；
5. 工作流在空 Maven 本地仓库中重新从 GitHub Packages 解析发布的注解工件，再创建同名 GitHub Release；在一个干净的消费者工程中导入 BOM、注解 API 和一个适配器，验证坐标与传递依赖。

`release` Profile 会为可发布 JAR 附加 source JAR 和 Javadoc JAR。Workflow 使用短期 `GITHUB_TOKEN`，不需要也不允许将 package token 写入仓库。消费者下载 GitHub Packages 时需以本机环境变量提供 classic PAT 的 `read:packages` 权限，详见 [deploy/README.md](../../deploy/README.md)。

Maven Central 的入口已写在 `.github/workflows/publish-central.yml`，但它与 GitHub Packages 是独立目标，且只能由 `maven-central` Environment 下的手动工作流执行。先验证 `io.github.vicliu624` Central Portal 命名空间，再在该 Environment 配置 `CENTRAL_USERNAME`、`CENTRAL_PASSWORD`、`MAVEN_GPG_PRIVATE_KEY` 和 `MAVEN_GPG_PASSPHRASE`。`central-release` Profile 强制发布版、非 SNAPSHOT 依赖、source/Javadoc 附件与 PGP 签名，并交由 Central Portal 插件生成校验和与 bundle；最后会从空本地仓库重新解析 Central 工件。完整的凭据和不可变版本规则见 [deploy/README.md](../../deploy/README.md)。

本机开发默认使用 `mvn install` 或 `mvn verify`；不要提交 `settings.xml`、token、签名私钥或 `workspace/local/`。

## 提交前清单

- 运行三项完整校验；
- 确认 `git status` 没有 `target/`、`node_modules/`、`workspace/local/` 或真实内容包；
- 确认新增 Maven 工件有清晰的发布理由与 BOM 决策；
- 确认新增技术依赖没有进入 `atlas-domain-model` 或 `atlas-annotations`；
- 确认新数据字段有来源状态和证据，不会把“推测”当作“已验证”；
- 确认业务用户默认视图只看到业务语言，源码与原始 payload 仍在受控专家模式。
