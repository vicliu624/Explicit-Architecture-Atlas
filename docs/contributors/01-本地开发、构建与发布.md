# 本地开发、构建与发布

## 前置条件

| 工具 | 基线 | 用途 |
| --- | --- | --- |
| JDK | 21 或更高 | 编译所有 Maven 工件；Parent POM 明确要求 21+ |
| Maven | 3.9 或更高 | 构建 Reactor、测试、生成处理器产物 |
| Node.js | 22 或更高 | 仅校验和构建独立 Web 工程 |
| PowerShell 7+ | 推荐 | 运行仓库结构校验脚本 |

Maven 模块使用 Java 21 的语言/字节码基线，以保证发布物可被 Java 21 环境消费。使用更高版本 JDK（例如 JDK 22）进行本地构建是允许的，只要 Maven Enforcer 校验通过。

## 第一次构建

在仓库根目录依次执行：

```powershell
mvn -B verify
npm --prefix ui-layer/atlas-web run check
pwsh ./scripts/verify-structure.ps1
```

三条命令检查的对象不同：

| 命令 | 验证内容 |
| --- | --- |
| `mvn -B verify` | Parent/BOM/Contract、所有可发布 JAR、Plugin、CLI、fixture 与 JUnit 测试 |
| `npm --prefix ... run check` | Web shell 的 JavaScript 语法；不需要安装前端框架依赖 |
| `verify-structure.ps1` | Reactor 是否包含关键模块、目录边界和关键文档是否存在 |

`integration-test/fixture-projects/strict-explicit-java-sample` 会在 Maven 编译过程中调用注解处理器。成功后可以检查其构建输出中的：

```text
target/classes/META-INF/explicit-architecture-atlas/atlas-intent.json
```

这证明最小闭环“通用显式架构样例 → 编译期意图索引”可用，且完全不依赖任何真实业务项目。

## 常用开发命令

只构建一个模块及其所需依赖：

```powershell
mvn -B -pl infra-driven/atlas-source-jvm -am test
```

只验证 Maven Plugin：

```powershell
mvn -B -pl infra-driving/atlas-maven-plugin -am verify
```

查看 CLI 当前命令面：

```powershell
java -jar infra-driving/atlas-cli/target/explicit-architecture-atlas-cli-0.1.0-SNAPSHOT.jar --help
```

运行结构脚本时请从任意目录调用完整脚本路径；脚本通过自身位置计算仓库根目录，不依赖当前工作目录。

## 新增一个分析适配器

假设要支持一种新的技术事实来源，按以下顺序实施：

1. 先在 `infra-driven/` 下创建 `atlas-<technology>-source` 模块；它只依赖 `atlas-analysis-spi` 和该技术 SDK。
2. 实现 `SourceFactsAnalyzer`，输出带证据的 `AnalysisResult`；不要让分析器直接返回 Web DTO 或写入浏览器缓存。
3. 在根 `pom.xml` 注册模块，并视其是否为公共稳定能力决定是否在 `atlas-bom` 管理版本。
4. 为该技术创建通用 fixture 或最小测试；不能依赖本机真实项目目录。
5. 在 `atlas-server-bootstrap` 中以可选方式装配它；“未启用”必须在数据中与“没有发现关系”区分。
6. 更新工程结构、依赖规则和产物契约文档。

若某能力是 Atlas 的输入方式（例如 Gradle 插件、IDE 命令），应放到 `infra-driving/`；若只是读取外部事实（例如 Kafka 消费状态），应放到 `infra-driven/`。

## 新增领域模型或契约字段

稳定模型变更需要同时考虑 Maven 兼容性和数据包兼容性：

1. 在 `atlas-domain-model` 中定义 JDK-only 类型，并保持构造器验证明确；
2. 如数据包也需要该概念，在 `atlas-contract` 中演进对应 Schema；
3. 更新 `schemaVersion` 的兼容策略，禁止让旧渲染器静默误读新字段；
4. 增加 fixture 与集成测试，验证事实、意图和内容的关联；
5. 在变更日志/ADR 中说明是否破坏二进制、源码或 Schema 兼容性。

不要为了图省事把 Spring、Axon 或 JSON 库类型放入领域记录。领域模型是发布边界最内层，技术类型会把所有消费者锁死在同一框架版本上。

## 发布流程

仓库当前只提供可发布的 Maven **边界**，没有提交任何仓库凭据、签名密钥或真实发布地址。正式发布应由受保护 CI 环境完成：

1. 在受保护 CI 注入 Maven `settings.xml`、签名密钥与目标仓库凭据；
2. 将版本从 `*-SNAPSHOT` 切换为发布版本，并验证 BOM 中的受管版本一致；
3. 执行完整 `mvn -B verify`、Web 语法检查和结构校验；
4. 先发布 Parent、BOM、Contract 与内层模型，再发布应用、SPI、适配器、Plugin、CLI 和 Server；Reactor 自身会处理本次构建的依赖顺序；
5. 在一个干净的消费者工程中导入 BOM、注解 API 和一个适配器，验证坐标和传递依赖；
6. 发布独立 Web 静态资源或容器镜像，版本号与其可消费的数据 Schema 范围一并记录。

仅在受控 CI 完成上述准备后才可执行类似命令：

```powershell
mvn -B -Prelease deploy
```

`release` Profile 会为可发布的 Java 工件附加 source JAR 和 Javadoc JAR；根聚合 POM 与测试模块明确跳过 deploy。发布仓库、签名、凭据和部署地址依然由受保护 CI 提供，而不写入项目 POM。

本机开发默认使用 `mvn install` 或 `mvn verify`。不要在 `pom.xml` 中硬编码私有仓库 URL，也不要把 `settings.xml`、token、签名私钥或 `workspace/local/` 纳入版本控制。

## 提交前清单

- 运行三项完整校验；
- 确认 `git status` 没有 `target/`、`node_modules/`、`workspace/local/` 或真实内容包；
- 确认新增 Maven 工件有清晰的发布理由与 BOM 决策；
- 确认新增技术依赖没有进入 `atlas-domain-model` 或 `atlas-annotations`；
- 确认新数据字段有来源状态和证据，不会把“推测”当作“已验证”；
- 确认业务用户默认视图只看到业务语言，源码与原始 payload 仍在受控专家模式。
